# AfterGlow — 시술 후 90일, 회복을 혼자 견디지 않도록

> 시술은 하루, 회복은 90일입니다.

AfterGlow는 미용 시술을 받은 사람이 **시술 다음 날부터 90일 동안** 매일 30초 기록으로 회복을 따라가는 웹 서비스입니다. 정지된 시술 리포트 대신, 오늘 내 상태에 맞춰 매일 다시 쓰이는 케어 플랜을 제공하고, 회복이 예상 범위를 벗어나면 시술받은 클리닉으로 연결합니다.

---

## 시연 계정

두 관점을 모두 확인하실 수 있도록 계정 2개를 제공합니다.
**로그인 화면 하단의 버튼을 누르면 입력 없이 바로 들어갑니다.**

| 구분 | 이메일 | 비밀번호 | 보게 되는 것 |
| :-- | :-- | :-- | :-- |
| 사용자 | `demo@afterglow.kr` | `AfterGlow2026!` | 회복 중인 환자 화면 (리프팅 D+12 시나리오) |
| 클리닉 관리자 | `clinic@afterglow.kr` | `Clinic2026!` | 리콜 대시보드 (공유받은 기록 + 답변) |

> 두 계정의 데이터는 전부 임의로 생성된 더미이며 실제 환자 정보를 포함하지 않습니다.
> 시연 시나리오는 D+12를 기준으로 작성되어 있으며, `select public.rebase_demo_data();` 를
> 실행하면 언제든 KST 오늘 기준 D+12로 되돌아갑니다.

### 3분 시연 순서

1. **사용자로 보기** → `오늘` 화면에서 D+12, 오늘의 케어 카드, 오늘 피할 것/할 것 확인
2. `회복` 탭 → 예상 회복 곡선 위에 내 기록이 겹쳐진 그래프, D+8 이탈 알림과 클리닉 답변 확인
3. `컨디션` 탭 → 수면·스트레스 입력이 회복 속도 기대치를 몇 %로 바꾸는지 확인
4. `오늘 컨디션 기록하기` → 5개 탭으로 30초 체크인. 증상을 높게 입력하면 **이탈 감지**가 즉시 발동
5. `회복` 탭에서 새 알림을 **클리닉에 공유**
6. 로그아웃 → **클리닉으로 보기** → 방금 공유된 기록이 미답변으로 올라온 것 확인 → 답변 전송
7. 다시 **사용자로 보기** → 그 답변이 사용자 화면에 도착한 것 확인

## 왜 이 문제인가

기존 웰니스·뷰티 서비스는 거의 전부 **"시술 전"** 에 몰려 있습니다. 병원 탐색, 가격 비교, 리뷰, 예약. 정작 사람이 가장 불안한 구간은 그 다음입니다.

| 시술 후 실제 문제 | 지금의 대응 |
| :-- | :-- |
| "이게 정상인가요?" — 매일 드는 질문 | 답을 아는 사람은 클리닉에, 불안한 사람은 집에 |
| 시술 리포트가 앱에 있지만 **조회만 가능** | 오늘 내 상태에 맞춰 바뀌지 않는 정지된 문서 |
| 금기는 시술 당일 구두로 한 번 안내 | "2주간 사우나 금지"를 12일째에 기억하는 사람은 없음 |
| 언제 다시 해도 되는지 아무도 안 알려줌 | 사용자는 계속 참거나, 그냥 해버림 |
| 회복이 이상해도 판단 기준이 없음 | 참다가 늦게 내원하거나, 괜찮은데 불필요하게 내원 |

## 핵심 기능

### 1. 하루 30초, 사진 없는 체크인
붓기 · 붉은기 · 통증 · 각질 · 당김 5가지를 **탭 한 번씩**. 각 단계에는 숫자가 아니라 상황 문장이 붙습니다("사진에서 티가 남", "화장으로 가려짐"). 사진은 선택. 실제 소요 시간을 저장해 UX 지표로 추적합니다.

> 사진 기반 AI 진단을 핵심 축으로 쓰지 않은 것은 의도적입니다. 조명·각도 편차가 크고, 의료기기 규제 영역에 닿으며, 무엇보다 매일 하기에 무겁습니다.

### 2. 예상 회복 곡선 위에 내 기록 겹치기
시술별 프로토콜에서 증상마다 기대 곡선(peak → onset → 반감기 지수감쇠)을 생성하고, 실제 체크인을 그 위에 겹쳐 그립니다. **"지금 이 상태가 정상인가요?"에 매일 답이 나옵니다.**

### 3. 매일 새로 쓰이는 케어 카드
경과일 + 어제 기록 + 수면·스트레스 + 자외선·습도를 읽고 **오늘 피할 것 / 오늘 하면 좋은 것**을 만듭니다. 그리고 **오늘 막 풀린 금기**를 먼저 알려줍니다 — 사용자가 가장 기다리는 정보입니다.

생성 책임을 두 층으로 나눈 것이 이 카드의 설계 핵심입니다.

| 항목 | 생성 주체 | 이유 |
| :-- | :-- | :-- |
| 금기·권장 **목록** | 규칙 엔진 (시술 프로토콜) | 항상. LLM이 금기를 창작하면 의료 안전성이 깨진다 |
| 오늘의 **문장** | 기본은 규칙 엔진, `ANTHROPIC_API_KEY` 연결 시 Claude API | 문장은 표현의 문제라 LLM이 맡아도 안전하다 |

> **현재 배포본은 규칙 엔진 문장으로 동작합니다.** Claude API 연동은 구현·검증이 끝나 있고
> (`app/api/care-card/route.ts` — 프롬프트 생성, 진단성 표현 검증, 실패 시 폴백),
> 시연 비용을 통제하기 위해 키를 연결하지 않은 상태입니다.
> 환경 변수 한 줄로 전환되며, **카드에는 어느 쪽이 문장을 썼는지 그대로 표기**됩니다.

규칙 엔진 문장도 고정 문구가 아닙니다. 풀린 금기 → 몸 상태 경고 → 단계 전환 → 환경 → 순항 순으로
우선순위를 평가해 그날의 문장을 고르고, 순항 문구는 경과일로 갈라 씁니다.

### 4. 수면·스트레스로 회복 기대치 보정
잠을 못 잔 주에는 회복이 느린 것이 **정상**입니다. 그런데 기존 서비스는 모두에게 같은 기대치를 들이댑니다. AfterGlow는 최근 3일 수면·스트레스·음주로 회복 속도 기대치를 0.7~1.2배 범위에서 보정합니다.

> 웨어러블 연동을 쓰지 않았습니다. 웹만으로 완결되어야 하고, 기기가 없는 사용자를 개인화에서 제외하고 싶지 않았습니다. 세 가지 자가 보고만으로 충분히 동작합니다.

### 5. 이탈 감지
실측이 보정된 기대치를 1.2 이상 초과하면 알림이 생성됩니다. 무엇이 얼마나 달랐는지 숫자로 보여주고(`붓기 예상 0.6 → 기록 3`), 불안을 키우지 않는 다음 행동을 제시합니다.

### 6. 클리닉 리콜 대시보드
사용자가 켜둔 경우에만, **이탈이 감지된 알림 1건 + 그 전후 3일 기록**이 시술받은 클리닉에 전달됩니다. 의료진은 증상 표와 메모를 보고 답변하거나 내원을 권고할 수 있고, 그 답변은 사용자 화면에 바로 도착합니다.

이 범위는 UI가 아니라 **DB가 강제**합니다. 동의가 꺼져 있으면 공유 시도 자체가 트리거에서 거절되고, 의료진 계정은 공유된 알림과 그 전후 3일 외에는 조회 자체가 불가능합니다.

### 7. 시술마다 다른 회복 곡선
리프팅 · 레이저 토닝 · 스킨부스터 · 필러 · 보툴리눔 톡신 · 화학적 필링 6종이 각각 다른 곡선, 다른 금기 기간, 다른 단계 설명을 갖습니다. 레이저 토닝은 "각질 뜯기"가 최우선 금기지만, 필러는 "얼굴 마사지"가 핵심입니다.

## 기존 서비스와 다른 지점

| | 기존 뷰티·웰니스 앱 | AfterGlow |
| :-- | :-- | :-- |
| 시간축 | 시술 **전** (탐색·예약) | 시술 **후** 90일 |

| AI 역할 | 사진으로 상태 판정 | 오늘의 행동 안내 생성 (금기는 규칙 엔진이 보증) |

| 리포트 | 조회용 정지 문서 | 매일 갱신되는 케어 플랜 |
| 클리닉 관계 | 예약 알선 | 이탈 시 리콜 |

## 기술 구조

```
app/
├── page.tsx                  # 랜딩
├── (auth)/                   # 로그인 · 회원가입 · 온보딩(시술 등록)
├── (app)/                    # 사용자 화면
│   ├── today/                # D+N, 케어 카드, 체크인 CTA
│   ├── checkin/              # 30초 체크인 플로우
│   ├── recovery/             # 회복 곡선 · 단계별 프로토콜 · 알림 이력
│   ├── vitals/               # 컨디션 입력 · 회복 속도 보정 · 상관 분석
│   ├── journal/              # 기록 · 빈 날 채워넣기 · 지난 여정
│   ├── profile/ settings/
├── (clinic)/clinic/          # 클리닉 리콜 대시보드
└── api/care-card/            # 문장 생성 경계 (규칙 엔진 ↔ Claude API 교체 지점)

lib/
├── recovery.ts               # 회복 엔진 (곡선 생성, 보정, 이탈 감지, 상관)
├── careCard.ts               # 케어 카드 생성기 + LLM 프롬프트 빌더
└── supabase/                 # 클라이언트 · 행↔도메인 매퍼 · DB 타입

services/                     # 화면 단위 조회 (Supabase 단일 경로)
mock/protocols.ts             # 시술 6종 케어 프로토콜 (마스터 데이터)
supabase/migrations/          # 스키마 · RLS · 동의 강제 트리거
middleware.ts                 # 세션 갱신 + 역할 기반 라우트 보호
```

**Next.js 14 (App Router) · TypeScript · Tailwind · Recharts · Framer Motion · zustand · Supabase**
<sub>Claude API 연동은 구현되어 있으며 환경 변수로 활성화됩니다.</sub>

### 설계 원칙

1. **회복 엔진은 순수 함수** — `lib/recovery.ts`의 모든 계산은 부수효과가 없습니다. 화면의 숫자는 하드코딩된 목업이 아니라 실제 계산 결과이고, DB의 `build_expected_curve()`가 같은 규칙을 재현합니다.
2. **접근 통제는 DB에서** — 모든 테이블에 RLS. 공유 동의는 트리거가 강제합니다. 프론트 버그로도 뚫리지 않습니다.
3. **모바일 퍼스트** — 회복 체크인은 침대에서 한 손으로 합니다. 탭 타깃 최소 36/44/52px, 하단 안전 영역 대응, PWA 설치 지원.
4. **의료 안전 표현** — 진단·질병·확정 표현을 쓰지 않습니다. 모든 계산 결과에 `<MedicalDisclaimer />`와 근거를 함께 노출합니다.
5. **빈 화면을 만들지 않습니다** — LLM 키가 없거나 호출이 실패해도 규칙 엔진 문장이 그 자리를 채우고, 지난 기록이 비면 채워넣기로 이어집니다.

## 로컬 실행

```bash
npm install
```

```bash
npm run dev
```

`.env.local.example`을 `.env.local`로 복사하면 바로 동작합니다. Supabase 공개 키는 코드에 기본값으로 들어 있어 별도 설정 없이 실행됩니다(접근 통제는 전부 RLS 담당).

| 변수 | 설명 |
| :-- | :-- |
| `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY` | 미설정 시 코드 기본값 사용 |
| `ANTHROPIC_API_KEY` | 설정 시 케어 카드 **문장만** Claude가 생성. 미설정 시 규칙 엔진 문장 사용 (기본값) |
| `SUPABASE_SERVICE_ROLE_KEY` | 서버 전용. 클라이언트 번들에 포함되지 않음 |

## 데이터 및 개인정보

**본 저장소와 시연 계정의 모든 데이터는 임의로 생성된 더미입니다.** 실제 고객 데이터나 실제 의료기관 정보를 포함하지 않습니다.

시술명 · 시술일 · 방문 병원은 개인정보보호법상 **건강에 관한 민감정보**입니다.

- 온보딩에서 별도 동의 항목으로 분리 수집, 기본값은 **비동의**
- 클리닉 공유는 동의 + 이탈 감지 시에만, 알림 1건 + 전후 3일 기록으로 범위 한정
- 동의가 꺼져 있으면 DB 트리거가 `CONSENT_REQUIRED`로 공유를 거절
- 체크인 사진은 비공개 버킷 + 사용자 폴더 정책, 서명 URL로만 접근
- 설정에서 전체 내보내기(JSON) 및 삭제 가능

상세 규격: [docs/frontend-backend-contract.md](docs/frontend-backend-contract.md)

## 의료적 안내

AfterGlow는 시술 후 회복 과정을 기록하고 안내하는 서비스로, 의료적 진단이나 치료를 대신하지 않습니다. 회복 곡선과 케어 카드는 입력된 기록과 시술 프로토콜을 바탕으로 계산된 참고 정보이며, 회복 속도 보정 계수는 의학적 확정 수치가 아닌 서비스 내부 가중치입니다. 통증이 갑자기 심해지거나 한쪽만 붓는 등 평소와 다른 변화가 있으면 시술받은 의료기관에 상담을 요청하세요.
